# harness-audit

このリポジトリのハーネス(Claude Code 向けの規約・agent・skill 定義一式)が、追加・変更を重ねるうちに重複・矛盾・陳腐化を起こしていないかを棚卸しする。**ファイルの編集は一切行わず、レポートを出力するだけ**の読み取り専用タスク。

## 対象範囲

- `CLAUDE.md`
- `AGENTS.md`
- `.claude/rules/*.md`
- `.claude/agents/*.md`
- `.claude/skills/*/SKILL.md`(プロジェクトローカルの skill のみ。グローバル skill は対象外)
- 上記 `.claude/skills/*/SKILL.md` から相対リンクで参照されている、同じ skill ディレクトリ配下のリポジトリ内文書(例: `.claude/skills/payload/reference/*.md`)。`SKILL.md` からの参照を起点に再帰的に辿り、以下のいずれかに該当したら打ち切る
  - 参照先が `.claude/skills/` の外
  - 外部 URL
  - 既に対象範囲に含めたファイル(循環参照)

## 進め方

対象ファイル(上記の再帰的に辿った文書を含む)をすべて読んだうえで、以下7観点をこの順で確認する。各観点で見つかった事象は、次の「出力形式」に従って記録する。

1. **重複・矛盾**: 対象ファイル群を横断で読み、同趣旨の記述や矛盾する記述がないか突き合わせる
2. **一度きりの事故対策の過度な一般化**: ルールごとに `git log -p -- <file>` でそのルールを追加したコミットを特定し、コミットメッセージ・当時の経緯が示す事象の具体性と、実際のルール文言の適用範囲の広さを比較する。特定の事故を起点にしながら適用範囲が広すぎる記述を候補として挙げる
3. **未使用の skills / agents**: 実行ログが存在しないため、実際に呼び出された回数や利用実績そのものは判定できない。skill は `description` に基づく自動選択やユーザーによる明示指定(`/<name>`)、agent はオーケストレーターからの明示指定で起動されるため、他のハーネスファイルにその名前が書かれていないことは未使用の根拠にならない(名前言及は agent 間の明示的な連携経路を確認する補助情報に留め、未使用候補の根拠には使わない)
    - `description` が前提とする対象(パッケージ名・機能・コマンド等)が現在のリポジトリに存在しない場合のみ「前提陳腐化候補」として提示する
    - 上記に当たらないものは、利用実績が判定不能である旨を明記したうえで候補に含めない(全件を候補として出さない)
4. **agent 間の責務重複**: `.claude/agents/*.md` の frontmatter `description` と本文の担当範囲(パッケージ・観点)を突き合わせ、重複や境界の曖昧さがないか確認する
5. **Codex からの繰り返し指摘**: `ai-communication/review_*.md` は gitignore 済みで永続しないため、`git log --oneline` 上で `docs(root): require ...` のようなルール追加コミットを時系列で並べ、テーマの重複がないか確認する。生のレビュー内容が残っていない制約のもとでの近似指標として扱う
6. **長大化による重要ルールの埋没**: 「著しく長い」を絶対値で判定せず、今回の対象ファイル群の中での相対比較で判定する
    - 対象ファイルを種別(`CLAUDE.md`/`AGENTS.md` のような単独文書、`.claude/rules/*.md`、`.claude/agents/*.md`、`.claude/skills/**` の4グループ)に分け、グループ内の行数の中央値を求める
    - 行数がグループ内中央値の2倍を超えるファイルを「長大化候補」として挙げる
    - 1つの見出し配下(次の同階層以上の見出しが現れるまで)の行数がファイル全体の40%を超えるセクションを「特定セクションへの偏り候補」として挙げる
    - いずれも今回実行時点での相対的なヒューリスティックであり、絶対的な「長すぎる/短すぎる」の判定ではない旨を出力に明記する
7. **現行フローとの乖離**: 対象ファイル全体(上記の再帰的に辿った文書を含む)に書かれたコマンド・パス・パッケージ名・構成・ツールバージョン等の検証可能な事実を、対応する一次情報(各 `package.json` の scripts、実際のディレクトリ構成、`package.json`/`bun.lock` の依存関係バージョン等)と照合し、一致しないものを候補として挙げる

## 出力形式

対象ファイルは一切編集せず、チャット上に構造化したレポートを出力する。観点(上記1〜7)ごとに `###` 見出しでグルーピングし、各指摘は以下の形式で自己完結させる。

```
- file: path/to/file:line
- category: duplicate | over-generalized | unused-candidate | responsibility-overlap | repeated-feedback | too-long | stale
- summary: 一文で問題を要約
- evidence: 判断の根拠(参照した記述・コミット等)
- suggested_action: integrate | delete | keep | needs-confirmation
```

指摘が無かった観点も `### 確認済み(問題なし)` として明記する。

## やらないこと

- 対象ファイルの編集・削除・統合(レポートのみ。是正は別タスクとして通常の実装前確認ルール + ai-communication フローに乗せる)
- 「未使用」「繰り返し指摘」を実行ログの裏付けなしに断定すること(候補提示とユーザー確認に留める)
- レポートを `ai-communication/` 配下に書き出すこと(この skill の出力はチャット上のみ。`ai-communication/result_*.md` は通常タスクフロー専用)
