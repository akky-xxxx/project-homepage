# 実装前確認ルール

- コードを書く/編集する全てのタスクにおいて、実装(Edit / Write 等によるコード変更)に着手する前に、設計・実装方針をユーザーに提示し、明示的な承認を得てから実装を開始する
  - 対象はページ・機能追加のような大きなタスクに限らず、1行の修正であっても例外なく適用する
  - 自分(agent)だけで設計内容を判断して実装を進めるのは不可。必ずユーザーの承認を待つ
  - 提示する内容の例: 変更対象のファイル/ディレクトリ構成、主要な設計判断とその理由、テスト方針
  - 実装作業を伴うタスクでは Plan Mode (EnterPlanMode) に入り、ExitPlanMode でユーザーの承認を得てから実装(Edit/Write 等)を開始する
  - 「確認を省略して自律的に進めてよい」という既定動作(auto mode 等)よりも本ルールを優先する

## Plan Mode の承認と設計レビューの関係

- ExitPlanMode の承認は「着手してよい」の承認であり、設計内容が妥当であることの検証ではない
- `CLAUDE.md` の ai-communication フロー手順2 で設計フェーズの対象となるタスクでは、ExitPlanMode で承認を得た後も実装に着手しない。そのターンの作業は「設計のみの result を作成する」ことであり、その旨をプランに明記してから ExitPlanMode する

## 基盤の置き換えを伴うタスク

- 既存実装を別の基盤(フレームワーク標準コンポーネント、ライブラリ、共通ユーティリティ等)へ置き換えるタスクでは、設計時に置換前の挙動を洗い出し、置換後も維持されるもの・失われるものを列挙する
- 失われる挙動を意図的に落とす場合、その可否を自分の価値判断で確定させず、ユーザーの承認を得てから実装を進める
- result の申し送りに「判断がほしい」と書くことは承認の代替にならない。承認を要する判断は、実装を確定させる前にユーザーへ提示し、応答を待つ
- 既存の規約(生成物を手で編集しない等)からの逸脱に対する承認(`CLAUDE.md` のレビュー対応手順)と同様、検証できたことは承認を得たことの代替にならない

## 実現手段が分岐するタスク

- 目的(例: 「見た目に統一感がない」)だけが示され、実現手段が複数考えられるタスクでは、1案に絞ったプランを提示する前に、選択肢とその前提をユーザーに確認する
- 入力元が issue かユーザーの直接指示かを問わず適用する
- 既存コードの延長を暗黙の既定にしない
- ExitPlanMode のリジェクトが繰り返される場合、プランの粒度ではなく前提確認漏れを先に疑う
